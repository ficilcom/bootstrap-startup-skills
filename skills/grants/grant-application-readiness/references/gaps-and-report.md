# ギャップと報告書

## 期限逆算

準備項目は互いに依存する。GビズIDが無ければ電子申請できず、納税証明書が無ければ認定支援機関の確認に進めない。したがって、各項目の着手期限は**その項目より後ろに続く鎖の長さ**で決まる。

計算:

- `depends_on` は「この項目より先に終わっていなければならない項目」を並べる。
- `downstream_lead_days[x]` = x に依存する項目の鎖のうち、リードタイムの合計が最も長いもの。
- `finish_by[x]` = 締切日 − `downstream_lead_days[x]`。
- `latest_start_date[x]` = `finish_by[x]` − x のリードタイム。
- `slack_days[x]` = `latest_start_date[x]` − 基準日。負なら既に着手期限を過ぎている。
- `critical_path` は `minimum_slack_days` を実現する鎖であり、ここが遅れると全体が遅れる。
- 既に `held` の項目はリードタイムを0として扱う。

依存が循環している場合は拒否される（`a -> b -> a`）。循環は依存関係の記述ミスであり、逆算できない。

リードタイムの見積:

| 発行元 | 目安の考え方 |
| --- | --- |
| `external_authority`（税務署、自治体、法務局、年金事務所） | 窓口・郵送・電子で大きく変わる。**発行までの日数だけでなく、請求してから手元に届くまでを含める。** 年度末や連休前は伸びる |
| `external_vendor`（見積先、工事業者） | 相見積が必要な場合は、依頼から回収までを1件ずつではなく並行で数える |
| `expert`（認定支援機関、税理士、社労士） | 相手の稼働に依存する。先に予約を取る行為自体を1項目として置く |
| `internal` | 自社で完結するが、他項目の完了待ちが入りやすい |

**リードタイムを希望的に短縮しない。** 不明な場合は `unknown` とし、必須項目にひとつでも不明なリードタイムがあれば `readiness_status` は `indeterminate` になる。逆算できない状態を、余裕があると読み替えない。

有効期限のある書類（納税証明書、登記事項証明書など）は `expires_on` を置く。締切より前に切れるものは、取得済みであっても `expiring_before_submission` として取得し直しの対象になる。**早く取りすぎることも失敗になりうる。**

## ギャップの優先順位

埋める順序は次のとおり。上から順に、下を先に埋めても無意味になる度合いが大きい。

1. **ゲート（適格性）**。`ineligible` があれば、他をすべて埋めても対象にならない。`grant-subsidy-fit` に戻す。
2. **着手期限を過ぎた必須項目**。`slack_days` が負の必須項目は、締切に間に合わない。締切を諦めるか、リードタイムの前提を変えられるかを先に決める。
3. **必須の書類・アカウント**。取得に外部の時間がかかるものから着手する。文章はいつでも書けるが、書類は待つしかない。
4. **必須記載項目の根拠**。`evidence_backing` が `unknown` または `estimated` の必須項目。**根拠の欠落は、文章の磨き込みに常に優先する。** 根拠のない主張は、審査でも交付後の実績報告でも崩れる。
5. **加点要件**。義務を引き受けられると確認できたものだけを取りに行く。`obligation_accepted` が未確認の加点は、埋めるべきギャップではなく、先に意思決定すべき論点である。
6. **文章の完成度**。`draft` から `reviewed`・`final` へ。第三者の確認を入れる時間を逆算に含める。
7. **任意項目**。上が片付いてから。

工数が足りない場合（`hours_shortfall` が正）、削るのは下から順である。任意項目、文章の磨き込み、義務を引き受けられない加点の順で落とす。必須の書類と根拠を削って締切に間に合わせた申請は、採択されても交付後に問題になる。

## 不採択でも残る価値

補助金の申請準備は、採択されなくても残るものがある。工数を投じる判断は、期待額だけでなくこの残存価値を含めて行う。

- 事業計画と数値計画。金融機関との対話（`skills/finance/bank-loan-readiness/`）にそのまま使える。
- 設備・外注の見積。実際に投資するかを判断する材料になる。
- 原価と工程の整理。`skills/finance/unit-economics-diagnostic/` の入力になる。
- 認定支援機関・専門家との関係。次回公募や融資の相談先になる。
- GビズIDなどのアカウント。他の申請でも使える。

逆に、残らないもの: 当該回の様式に固有の記載、加点のためだけに作った資料、締切に追われて根拠なく作った数値。**残らないものに時間を使っているなら、それは締切までの工数配分を見直す理由である。**

報告書には、投じる工数のうち何が残り、何が残らないかを分けて書く。

## 報告書形式

次の見出しで日本語の報告書を書く。日付には必ず出典と確認日を、数値には証拠状態を添える。

### 意思決定サマリー

準備度の状態（`submission_path_clear` / `gaps_with_time` / `gaps_without_time` / `blocked` / `indeterminate`）、締切までの日数、最も早い着手期限、いま決めるべきことを3行以内で示す。採択の見込みには触れない。

### 前提と引き継ぎ

`grant-subsidy-fit` の総合判断とゲート要件のステータス、当日確認した4点（受付状態と締切、提出方法とアカウント要件、加点の配点と証明方法、必要書類と様式の版数）、確認日と出典。

### 記載項目の準備度

必須項目の準備度、全項目の準備度、`confidence_percent`、着手していない必須項目、`unsupported_final_sections`（文章は仕上がっているが根拠が確認されていない項目）。**準備度は採択確率ではない旨を明記する。**

### 加点要件

ステータス別の点数（確認済み・見込み・未確認・取れない）を**別々に**示す。合算した期待得点を書かない。事後義務と、それを引き受けるかの判断が未了の項目を明示する。

### 必要書類とアカウント

必要度・状態別の件数、着手していない必須項目、締切前に有効期限が切れる書類、証明資料が特定できていない加点。

### 期限逆算

クリティカルパス、最小の余裕日数、着手期限を過ぎた項目。項目ごとの `latest_start_date` を、発行元と依存関係を添えて示す。

### 工数

必要工数の合計、締切までの利用可能工数、不足分。不足する場合は、上の優先順位に従って何を落とすかの案を示す。工数が不明な項目がある場合は、合計が下限値である旨を書く。

### 埋める順序と次の行動

`gaps` を優先順位に従って並べ、それぞれに担当、着手期限、完了の判定基準を置く。外部への問い合わせ、見積依頼、専門家への相談は、実行直前に承認を得る対象として明示する。

### 不採択でも残るもの

投じる工数のうち、採択されなくても残る成果と、当該回にしか使えない部分。

### 不明点と次に確認する事項

`missing_inputs` と `status_reasons` に挙がった項目、それが結論のどこを変えうるか、誰にどの一次情報を確認するか、確認の期限。
